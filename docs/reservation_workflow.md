# Reservation Workflow Overview

This document explains how the VIP section reservation flow operates across the public site, the admin configuration, and the operational follow-up used at the venue. It focuses on how availability is calculated, how payments progress from intent to confirmation, and what happens when the QR receipt is generated for at-the-door validation.

## 1. Content and Inventory Inputs

1. **Admin-managed inventory** – Editors manage each section size (e.g., 4-top, 6-top, 8–10 guests) inside the site configuration UI. Every tier records:
   - `total`: the number of sections of that size the club wants to offer for the night.
   - `reserved`: the number already sold before the current session (synced from prior orders or the admin panel).
   - `visual` styling and descriptive copy shown in the carousel.
2. **Synchronized defaults** – The same schema is enforced in `frontend/src/types/content.ts`, `frontend/src/config/defaultSiteContent.ts`, and the backend validation layer so the UI, API, and seed data agree on the contract.
3. **Hero metadata** – The `/reserve` page reuses the landing hero configuration (`content.hero.backgrounds`) for art direction and SEO metadata, updated via `useSiteContentContext` when the route mounts.

## 2. Customer Booking Experience

1. **Availability summary** – When a guest opens `/reserve`, `ReserveTablePage` hydrates table tiers from `useSiteContentContext` and calculates live availability using the formula `available = total - (reserved + sessionReservations)` for each tier. The summary ribbon aggregates totals across all tiers so the guest sees open, reserved, and total counts at a glance.
2. **Tier carousel** – Guests cycle through the three section sizes in the carousel. Each card displays:
   - A three.js `TableVisual` rendering tuned to the tier’s colours and seating layout.
   - Copy describing capacity and vibe.
   - A live “Available” counter that updates whenever the guest completes a booking in the current session.
3. **Reserve CTA** – Selecting “Reserve” opens a full-screen modal anchored to the chosen tier ID. Modal state drives three progressive steps: guest details, payment, and confirmation.

## 3. Modal Steps and Validation

1. **Guest details step**
   - Required inputs: full name, email, guest count. Optional: phone number.
   - The form enforces basic validation (non-empty strings, email format, positive guest count) before continuing.
2. **Payment step**
   - Collects card number, expiry, and CVC with format checks (12–19 digits for cards, `MM/YY` expiry, 3–4 digit CVC).
   - If the tier has sold out during the session, the UI blocks payment submission and prompts the guest to pick another tier.
3. **Confirmation step**
   - After successful validation, the UI generates a deterministic confirmation code via `generateCodeSeed(tier, email)` and displays a QR preview generated by `createQrMatrix(seed)`.
   - The confirmation panel reiterates the payment success copy configured in content (`confirmationHeadline` and `confirmationSubtext`).

## 4. Availability Updates

1. **Session-level decrement** – Once payment succeeds locally, `sessionReservations[tier.id]` increments (capped at `tier.total`). The carousel’s availability indicator and the hero summary both reactively update so guests can see the reduced inventory without a full refresh.
2. **Persisted inventory** – To keep availability authoritative across devices, the backend should expose an endpoint that:
   - Atomically decrements remaining capacity for the tier when the payment provider confirms the charge.
   - Rejects over-capacity reservations and returns an updated availability snapshot so the UI can surface sold-out messaging.
3. **Reconciliation** – Nightly operations should reconcile `reserved` counts by ingesting both web orders and host-initiated reservations so the admin panel remains accurate before doors open.

## 5. Payment and Settlement Flow

1. **Payment processor integration** – Replace the placeholder card form with a hosted checkout element (e.g., Stripe Checkout or Square Web Payments SDK) to offload PCI DSS obligations while supporting 3D Secure and stored payment methods.
2. **Authorization lifecycle** – On submission, create a payment intent for the tier price, include metadata for tier ID and guest details, and confirm the payment via the provider’s client SDK.
3. **Post-payment webhook** – Listen for the processor’s `payment_intent.succeeded` (or equivalent) webhook. When received:
   - Persist the reservation with guest details, tier, and payment reference.
   - Decrement remaining availability in durable storage.
   - Trigger the confirmation email with QR code payload.

## 6. QR Receipt Generation and Delivery

1. **Code structure** – The confirmation code combines the tier ID, normalized email, and timestamp hash (`VIP-{TIER}-{hash}`) so it is unique per booking while remaining human-readable for manual lookups.
2. **QR payload** – Encode the confirmation code (and optionally a secure lookup URL) into a standards-compliant QR image. The in-app preview mirrors this via `QrPreview`, but production email should embed a PNG/SVG generated on the server to ensure universal scanning reliability.
3. **Email dispatch** – Use a transactional email provider (e.g., SendGrid, Postmark) to deliver the receipt. Include:
   - Reservation summary (tier, guest count, arrival time guidance).
   - The QR code image and plain-text code fallback.
   - Venue policies (ID requirements, dress code, refund terms).
4. **Door validation** – At check-in, staff scan the QR code, which should resolve to a secure endpoint that verifies:
   - The reservation is active for the event and not previously redeemed.
   - Payment status is `succeeded`.
   - Guest name matches valid ID if verification is required.
   After validation, mark the reservation as redeemed to prevent reuse.

## 7. Operational Safeguards

1. **Concurrency controls** – Implement optimistic locking or database transactions around availability decrements to avoid double-booking during peak demand.
2. **Fraud and chargeback monitoring** – Monitor repeated failed attempts and mismatched billing details, and feed suspicious events into manual review.
3. **Data protection** – Because the hosted payment element handles card data, the platform only stores minimal PII (name, email, phone). Ensure QR payloads exclude sensitive data and expire after the event.
4. **Disaster recovery** – Export nightly reservation manifests (CSV/PDF) with QR codes so the door team can continue scanning if connectivity drops.

## 8. Future Enhancements

- **Real-time sync** – Subscribe to WebSocket or SSE feeds for availability to reflect host-side reservations instantly.
- **Guest self-service** – Offer links for guests to modify arrival times or upgrade sections while enforcing availability constraints.
- **Analytics loop** – Feed reservation and redemption data into dashboards to forecast demand by tier and optimize pricing blocks.

## 9. Automation Hooks

- **Stable selectors** – The public reservation flow now exposes `data-testid` attributes that match the pattern `tier-card-{tierId}` for carousel cards, `availability-*` for summary counters, and `reservation-*` for modal steps/buttons so end-to-end tests can target UI states without relying on CSS classes.
- **Admin coverage** – The site configuration screen mirrors this convention with `reservation-` prefixed attributes on copy inputs, tier inventory fields, and the “Add section tier” button, enabling automation suites to seed content and verify availability math against the live API.
- **Template placeholders** – CTA fields in both the carousel and modal accept a `{price}` token. Tests should assert the placeholder remains intact in configuration payloads so runtime formatting (handled in `ReserveTablePage`) continues to inject the tier price automatically.
